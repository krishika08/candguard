# ADR 0001: Modular Architecture & Reader-Storage Decoupling for v0.2.0

- **Status:** Accepted
- **Date:** November 2026
- **Deciders:** CandGuard Core Architecture & Maintainers
- **Consulted:** Open-Source Engineering Guidelines (`AGENTS.md`)

---

## 1. Context & Problem Statement

CandGuard v0.1.0 established an experimental, local-first Python CLI for auditing entity-resolution candidate-generation (blocking) pipelines. It proved that disk-backed SQLite processing could handle up to 10,000,000 candidate pairs with zero runtime dependencies and predictable memory ceilings.

However, the v0.1.0 implementation was concentrated across three monolithic files (`audit.py`, `compare.py`, `cli.py`):
1. **Coupled Parsing & Ingestion:** Delimited text parsing (CSV/TSV) was directly bound to SQLite table schema creation, SQL batch inserts, and error handling.
2. **Columnar Ingestion Blocked:** Introducing support for columnar formats such as Apache Parquet was impeded because there was no clean boundary between how pairs are read from disk and how they are stored or indexed.
3. **Entangled Presentation Logic:** CLI formatting strings, markdown tables, and JSON schema formatting were interspersed with database queries and math routines.
4. **API Friction:** Programmatic Python users had to import from deep submodules (`candguard.audit.audit_candidates`) without structured typing or top-level module exports.

We needed an architectural foundation for v0.2.0 that separates concerns, enables future format extensions (Parquet) and advanced metrics (drift analysis, rule attribution), while strictly preserving:
- Python 3.10+ compatibility.
- Zero default runtime dependencies.
- Local-first execution without external network telemetry.
- Bounded memory usage via disk-backed processing.
- Exact CLI flag, text output, JSON schema 1.0, and exit code (`0`, `1`, `2`) contracts.

---

## 2. Decision Drivers

- **Zero Speculative Frameworks:** Do not add complex dynamic plugin registries, dependency injectors, or ORM frameworks. Use Python Standard Library structural protocols (`typing.Protocol`).
- **Zero Default Dependencies:** The base install of `candguard` must remain dependency-free (`dependencies = []`).
- **Strict Backward Compatibility:** Every existing public function signature, CLI flag, exit code, and JSON key must continue functioning identically without breaking existing CI pipelines.
- **Clear Isolation:** Input readers, storage backends, metrics computation, and presentation rendering must be decoupled into independent testable units.

---

## 3. Considered Options

### Option 1: Retain Monolithic Structure and Branch In-Place
- *Description:* Keep all audit logic inside `audit.py` and add `if is_parquet:` branches to existing reader routines.
- *Pros:* Minimal file churn.
- *Cons:* High cyclomatic complexity; tightly binds Parquet dependencies to the core audit loop; difficult to isolate unit tests; impedes future storage backend experiments.

### Option 2: Full Modern Data Stack Migration (DuckDB + Polars)
- *Description:* Replace SQLite with DuckDB and use Polars for streaming dataframe processing.
- *Pros:* Higher raw execution throughput on multi-core hardware; native out-of-the-box Parquet support.
- *Cons:* Introduces 30–60 MB of compiled C++ binary dependencies; breaks the core zero-runtime-dependency constraint; complicates minimal CI container installations.

### Option 3: Protocol-Based Decoupling with SQLite Core (Chosen)
- *Description:* Establish clean boundaries using standard Python protocols (`CandidateReader`, `StorageEngine`), isolate pure math into `metrics.py`, isolate text/JSON rendering into `reporting.py`, and expose clean root API functions in `candguard.__init__`. Keep SQLite as the standard storage engine and gate Parquet behind an optional `[parquet]` extra.
- *Pros:* Achieves full modularity without any external dependencies; preserves existing SQLite stability and performance; provides an explicit plug-in boundary for future Parquet readers.
- *Cons:* Moderate increase in internal module count (10 modules vs 4).

---

## 4. Decision Outcome

We selected **Option 3**.

The codebase is reorganized into the following architectural components:
1. **`candguard.models`:** Defines `AuditError`, `LinkageType`, and `TypedDict` schemas guaranteeing JSON schema 1.0 structural conformance.
2. **`candguard.readers`:** Defines the `CandidateReader` protocol and `DelimitedReader` (supporting CSV/TSV with header validation, whitespace stripping, and delimiter escape decoding). Provides `get_reader()` factory.
3. **`candguard.storage`:** Encapsulates SQLite work database creation, PRAGMA tuning, batch insertion, dedupe pair canonicalization, indexing, percentile queries, and reliable tempfile cleanup in `SQLiteStorageEngine`.
4. **`candguard.metrics`:** Pure mathematical routines for search-space reduction ratios, growth ratios, and unambiguous length-prefixed ground-truth SHA-256 v2 fingerprints.
5. **`candguard.reporting`:** Houses `render_text`, `render_compare_text`, and `report_json`.
6. **`candguard.audit` & `candguard.compare`:** High-level workflow orchestration modules that preserve legacy import paths and exact public signatures.
7. **`candguard.__init__`:** Exports `__version__ = "0.1.0"`, `audit_candidates`, `compare_reports`, and `AuditError` at the package root.

---

## 5. Consequences & Trade-offs

### Positive Consequences
- **Extensibility:** Implementing a Parquet reader in a future milestone requires only implementing the `CandidateReader` protocol; zero changes will be needed in `SQLiteStorageEngine` or `candguard.audit`.
- **Testability:** Input parsing, database indexing, and metric math can be tested in complete isolation without running end-to-end audit pipelines.
- **Ergonomics:** Python users can import clean entry points directly from `candguard`.
- **Zero Regressions:** 100% of existing unit tests pass without alteration.

### Negative Consequences / Trade-offs
- Internal module count increases from 4 to 10 files.
- Reader protocol yields generator batches, introducing minor indirection overhead (measured at < 0.5% difference in wall-clock time, fully eclipsed by SQLite disk I/O).

---

## 6. Known Limitations

- **Parquet Support Status:** Parquet reading is defined architecturally at the reader boundary; the actual `pyarrow` implementation is deferred to subsequent milestones. Attempting to audit `.parquet` files raises an explicit `AuditError` explaining the missing optional dependency.
- **SQLite Scale Boundary:** SQLite remains validated up to 10,000,000 candidate pairs. Workloads beyond 50,000,000 pairs may require parallel ingestion or alternative storage engines.
